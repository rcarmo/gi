# Derived workspace index: clause-level source findings

`features/search/workspace-index.feature` contains 23 Gi proposals derived from pinned Piclaw workspace indexing and Gi-specific safeguards. These are outside the frozen Classic/shared corpus. The existing lineage note, `docs/implementation/plans/indexing-lineage-20260922.md`, compares pinned source revisions and names the intentional Gi differences. The rows below identify mounted code and tests, but a test declaration or SQL fixture does not award the full scenario. A later pinned Piclaw 3.2.4 search-function probe tested the background-request boundary in memory; no index child, production Piclaw API or deployed Gi indexing acceptance was run.

Gi's accepted ADR-0046, ADR-0050 and ADR-0051 specify explicit refresh. Native `/api/workspace/index` accepts authenticated POST refresh and read-only GET status. `/api/workspace/search` reads committed data and rejects `refresh` query parameters (`internal/web/workspace_index.go`). The scheduler, worker, scanner, scoped store and UI/TUI controls are mounted; ordinary reads and native writes do not schedule background refresh. This is the current Gi policy, not a fresh parity award. The proposal at `:33` still asks search to trigger bounded background refresh. `PICLAW_DB_IN_MEMORY=1 bun tests/ux/oracle/piclaw-workspace-search-trigger-probe.ts` pins the installed release/source-map hash, uses an isolated workspace and in-memory SQLite, and intercepts the background requester before it can launch a child. A nonempty cold or stale notes search returned a committed hit and requested refresh; a ready search requested none, and an empty query returned an error without requesting refresh. This confirms the Piclaw **search-function request** boundary, not a bounded worker completion, production HTTP/UI journey or automatic freshness. Gi's accepted explicit-only policy at `:199` and `:211` differs from the observed oracle. Keep `:33` open pending an explicit policy decision; qualify `:199` and `:211` against their actual assertions. A stored invalidation is not an automatically processed one.
