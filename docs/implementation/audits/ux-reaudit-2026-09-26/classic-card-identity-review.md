# Classic card-submission identity, 28 September 2026

The installed Piclaw 3.2.4 Classic client filters persisted `adaptive_card_submission` blocks by typed identity. `make test-piclaw-card-identity` passed six Chromium/WebKit phone, tablet and desktop fixture cases. A valid `Action.Submit` block and a valid block with omitted action type rendered receipts. Empty or overlong card IDs, zero or unsafe post IDs, an invalid timestamp, and `Action.OpenUrl` did not render receipts. The fixture supplied timeline posts; no card was activated or written to storage.

Gi's `web/src/ui/adaptive-card-submission.ts` previously checked only field types. It now requires a non-empty `card_id` of at most 256 characters, a positive safe-integer `source_post_id`, a parseable `submitted_at`, and `Action.Submit` when `action_type` is present. Extraction defaults an omitted action type to `Action.Submit`, matching the installed Classic helper. A Bun support test covers the bounds and invalid cases, including the maximum safe post ID. `make test-ux-card-identity` passed six Chromium/WebKit cases against Gi's mounted HTTP/SQLite-backed fixture: it displayed only the valid and omitted-action receipts, kept the unsent draft and stored messages intact, and created no turns.

This is a bounded validation and display slice of `@ux-extra-002`. The frozen scenario describes the client building a submission. The fixture did not activate a card, test submission admission or persist a resulting receipt. Gi's mounted `submitAdaptiveCardAction` still rejects submissions before transport; `@ux-extra-002` remains unmapped. The separate `@ux-extra-003` rejection behaviour is not upgraded by these tests. No live chat, provider or production deployment was involved.
