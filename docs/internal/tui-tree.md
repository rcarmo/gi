# TUI /tree

`/tree` opens Pi's session tree navigator, `TreeSelectorComponent`
(`components/tree-selector.js`), and moves the session to the chosen point
as Pi's `navigateTree` does, with an optional summary of the branch being
left.

Code:

- `internal/tui/tree_selector.go`: the selector (Pi's `TreeList`,
  `TreeHelp`, `SearchLine` and `LabelInput`) and its keys.
- `internal/tui/session_tree.go`: the tree of gi sessions, navigation and the
  summary prompt.
- `internal/tui/editor_dialog.go`: Pi's `ExtensionEditorComponent`, used for
  "Summarize with custom prompt".
- `internal/compaction/branch_summary.go`: Pi's `generateBranchSummary` and
  `prepareBranchEntries`.
- `internal/turn/branch_summary.go`: the model call and the branch summary in
  the model context.
- `internal/store/session_tree.go`: branch sessions and labels.

Goldens, generated by Pi's own code:

| Script | Test |
| --- | --- |
| `scripts/golden-tree.mjs` | `TestTreeSelectorMatchesPi`: rows after each key, what Enter selects, labels and Ctrl+X copies, at two sizes |
| `scripts/golden-editor-dialog.mjs` | `TestEditorDialogMatchesPi` |
| `scripts/golden-branch-summary.mjs` | `TestBranchSummaryMatchesPi`: prompts, token budgets and summaries |

## Branches are sessions

Pi keeps every branch in one session file: entries point at their parent
and the session has a movable leaf. gi keeps one message list per session,
and the engine builds the model context from that list. A /tree branch in gi
is therefore a session:

- Navigating to a point that ends an existing branch switches to that
  branch's session.
- Navigating anywhere else copies the session up to that point
  (`store.BranchSessionBefore`). The copy records its source in the
  `tree_parent` state key. It keeps the source agent, channel and account,
  with a fresh logical chat and routing identity.
- The tree is the branch family: the root session and every session whose
  `tree_parent` chain leads to it. Copied messages carry
  `forked_from_message_id`, so a copy's history maps onto the original
  entries and the branches share it in the tree.
- The active branch is the current session. Pi lists the active branch first
  at each fork, and so does gi.

`/fork` and `/clone` copies drop `tree_parent` and the labels. They start
their own tree, as Pi's `/fork` and `/clone` start a new session file. Both
keep the source agent by default. `/fork` copies history before the selected
user message; `/clone` copies all history. Blank titles inherit the source
name. `/spawn [@agentN]` creates or opens a peer with the existing clipped-context
behaviour; the legacy `/fork @agentN` form still follows that peer path.

Each copy has its own session ID, opaque key, canonical scope signature and
aliases, using its new logical chat ID. It does not take the source's main
session flag or inbound channel binding. `/resume` or `/switch session_id`
selects an exact copy. `/switch @agent` retains the existing newest-session
list order when several sessions share an agent. An explicit different agent
in `/clone @agentN` requests a peer copy; naming the source agent keeps its
channel and account.

The web fork endpoint and `POST /api/sessions` with `fork_from` use the same
store contract: an omitted `agent_id` preserves the source agent; a different
explicit `agent_id` requests a peer copy. The fork response reports the
stored agent identity.

`make test-session-copy-identity` repeats store, TUI and web checks with the
race detector. Coverage includes concurrent copies, alias/key resolution,
main routing, history cutoffs, tree/summary navigation and peer commands.

## Copy profiling (2026-10-07)

On Go 1.27.1/linux-amd64, `make bench-session-copy` copies 100 messages of
1,024 bytes each into a file-backed SQLite database and deletes the copy to
bound the database size. Cleanup is timed equally in both runs; race checks
use a separate workload. Source revision: `ceb9fd2` plus this change.

| 100-message copy | Before batching | Transaction + prepared insert |
| --- | ---: | ---: |
| ns/op | 16,406,538 | 3,946,761 |
| B/op | 353,532 | 333,415 |
| allocs/op | 6,343 | 5,540 |

Cumulative CPU and both `alloc_space`/`alloc_objects` profiles identified
per-message SQLite insert and timestamp-update work. Copies now insert the
session, identity, aliases and messages in one transaction, reuse the message
insert statement and update the timestamp once. A triggered failure on the
second message rolls back the destination and its routing identity. Source
history/state stay unchanged. Remaining allocations mostly come from message
loading, payload decoding and the SQLite driver; no new cache was added.

Verification: 32 focused tests repeated three times under the race detector,
2,181 Go tests across 35 packages, vet and `CGO_ENABLED=0 make build` passed.
Profiling also found a tree-golden test that changed global `time.Local` while
pprof read the clock. Label times now use the injected clock's location, so
the golden fixes its clock to UTC without mutating process state. No browser
or PTY fixture rerun was performed. The review delegate timed out and supplied
no review result. Raw profiles, test binaries and disposable logs were removed
after analysis.

Entries are the session messages as Pi session entries (the `/export` JSONL
mapping in `internal/sessionexport`): user and assistant messages, tool calls
and tool results. gi compaction messages are `compaction` entries and branch
summaries are `branch_summary` entries. gi system notices are `custom`
entries, which only the "all" filter shows.

## Navigation

Selecting an entry follows Pi:

- The current leaf: "Already at this point".
- A user message: the target is its parent, and the message text goes back to
  an empty editor.
- Anything else: the target is the entry.

Pi then asks "Summarize branch?" with "No summary", "Summarize" and
"Summarize with custom prompt". Escape returns to the tree with the entry
still selected. Cancelling the custom instructions returns to the question.
`branchSummary.skipPrompt` skips the question and does not summarize.

A summary covers the current session's messages after its common ancestor
with the selected entry, as Pi's `collectEntriesForBranchSummary` does. The
session model writes it with Pi's prompt, budget (`branchSummary.reserveTokens`,
default 16384) and file lists. "Summarizing branch... (Esc to cancel)" shows
while it runs; Escape cancels and reopens the tree. The summary is a user
message with `kind: branch_summary` at the end of a new copy of the target
branch, as Pi adds a `branch_summary` entry under the target. The model sees
it wrapped in Pi's branch summary prefix and suffix. The transcript shows it
as a "Branch summary" block.

## Labels

Shift+L edits the selected entry's label and Shift+T shows label times, as in
Pi. Labels are stored in the family root's `tree_labels` state, keyed by entry
ID, with the time they were set. Pi appends `label` entries to the session
file instead.

## Settings

- `treeFilterMode`: the filter /tree opens with. `/settings` lists it as
  "Tree filter mode", as Pi does.
- `branchSummary.reserveTokens` and `branchSummary.skipPrompt`.

## Differences from Pi

- Navigating to a new point creates a session, which `/resume` lists. Pi
  moves the leaf within one file.
- Pi aborts a streaming response before navigating. gi switches sessions and
  the previous session's turn continues there.
- Extension hooks `session_before_tree` and `session_tree` are not ported.
- Summaries serialize tool-call arguments in key order (Go maps). Pi keeps
  insertion order. The golden uses arguments already in key order.
- `/tree` is a TUI command. The web UI does not offer it, and its timeline
  shows a branch summary as a user message.
